# OPS-004 — Gemessen / Geschlossen / Offen

## Description

Ein Audit endet selten sauber. Fast immer bleibt ein Rest: eine Zahl, die nicht ganz aufgeht, ein Verhalten, für das die Belege nicht reichen. In genau diesem Moment ist die Versuchung am grössten, eine plausible Erklärung zu formulieren und weiterzugehen — und genau da entsteht der Fehler, den dieser Katalog an anderer Stelle bereits verbietet.

`FID-003` hält fest, dass ein Server eine Leermenge nicht für den Aufrufer deuten darf. Dieser Check überträgt dieselbe Regel auf den Auditor: **Ein Audit-Report darf einen unerklärten Rest nicht für den Leser deuten.** Der Fehlermodus ist identisch, nur eine Ebene höher, und er ist gefährlicher — ein Audit-Report ist das Dokument, auf dessen Grundlage über Produktionsfreigaben entschieden wird.

Der reale Fall, aus dem dieser Check stammt, ist der Nachlauf zu [`termdat-mcp#11`](https://github.com/malkreide/termdat-mcp/issues/11). Nach der Behebung des eigentlichen Bugs blieb eine Differenz: Die Weboberfläche zeigte 12 Einträge, die API lieferte bei maximalem Recall 7. Dazu wurde eine plausible Erklärung veröffentlicht — das Web-UI zähle Benennungen statt Einträge, also eine Zähldifferenz, kein Recall-Problem. Die Formulierung war als Vermutung gekennzeichnet und trotzdem falsch. Der Melder schickte die zwölf Entry-IDs; sie waren alle verschieden. Die Wahrheit war unbequemer: Zehn der zwölf Einträge liefert die API überhaupt nicht aus, auch nicht beim gezielten Abruf per ID.

Die Vermutung stand zwei Tage lang als quasi-Ergebnis im Raum. Hätte niemand nachgefragt, wäre sie zur Dokumentation geworden.

Das Muster ist verallgemeinerbar und hat drei Ausprägungen:

| Ausprägung | Wie es klingt | Warum es Schaden anrichtet |
|---|---|---|
| Vermutung als Ergebnis | «vermutlich eine Zähldifferenz» | Wird beim Zitieren zur Tatsache; die Kennzeichnung überlebt die erste Weitergabe nicht |
| Rest weggerundet | «im Wesentlichen deckungsgleich» | Die Differenz verschwindet, ohne dass jemand sie je gemessen hat |
| Abwesenheit von Belegen als Beleg | «keine Hinweise auf X gefunden» → Status `pass` | Nicht gesucht und nichts gefunden sind nicht dasselbe |

`high`, nicht `medium`: Ein einzelner falscher Befund ist ärgerlich; ein Report, der Vermutungen und Messungen vermischt, macht **alle** seine Befunde unzuverlässig, weil dem Leser das Unterscheidungsmerkmal fehlt.

## Verification

### Modus 1: documentation_check (Report-Struktur)

```bash
# Trennt der Report Gemessenes von Geschlossenem?
grep -nE '^#+.*(Gemessen|Geschlossen|Offen|Measured|Inferred)' <audit_dir>/audit-report.md

# Vermutungssprache ausserhalb eines als solchen markierten Abschnitts
grep -nEi 'vermutlich|wahrscheinlich|dürfte|scheint|vermutet|anzunehmen|presumably|likely|appears to' \
  <audit_dir>/audit-report.md <audit_dir>/findings/*.md
```

**Pass-Pattern** — jedes Finding und der Report tragen die drei Abschnitte, und Vermutungssprache steht ausschliesslich unter «Geschlossen» oder «Offen»:

```markdown
### Gemessen
- API liefert 7 Einträge bei maximalem Recall (alle 23 Klassifikationen, alle
  11 Feld-Flags, Wildcards, alle Sprachen), gemessen 2026-07-30.
- Weboberfläche zeigt 12 Einträge zum selben Begriff, IDs vom Melder geliefert.
- `/v2/Entry` je ID einzeln: 2 von 12 ausgeliefert, 10 mit leerem Body.

### Geschlossen
- Die fehlenden Einträge sind nicht durch einen Filter verdeckt, sondern werden
  nicht ausgeliefert. Begründung: gezielter ID-Abruf umgeht jede Suchlogik.

### Offen
- Nach welchem Kriterium die API auswählt, ist unbekannt. Der Statusunterschied
  bei 1557 («In Bearbeitung») ist ein Indiz, kein Beleg. Angefragt bei der
  Bundeskanzlei am 2026-07-30; Antwort ausstehend.
```

**Fail-Pattern:**

```markdown
Die Differenz von 7 zu 12 Treffern ist vermutlich eine Zähldifferenz —
das Web-UI zählt wahrscheinlich Benennungen statt Einträge.
```

Formal als Vermutung markiert, inhaltlich als Erklärung platziert, und beim Weiterzitieren wird daraus «ist eine Zähldifferenz».

### Modus 2: code_review (Status-Vergabe)

Jeder Check mit Status `pass` braucht einen positiven Beleg, nicht bloss die Abwesenheit eines Negativbelegs. Ein leerer `grep` ist kein `pass` — er ist ein `pass` nur dann, wenn das Suchmuster nachweislich greifen *würde*, wenn das Anti-Pattern vorhanden wäre.

```bash
# Findings/Results mit pass-Status, deren Evidence nur aus Leer-Outputs besteht
python tools/aggregate_results.py validate <audit_dir>
grep -L "Excerpt\|Output:\|Zeile" <audit_dir>/findings/*.md
```

Wo ein `pass` nicht belegbar ist, lautet der Status `not_verified` — und der Check landet unter «Offen», nicht unter den bestandenen.

## Pass Criteria

- [ ] Der Audit-Report enthält die Abschnitte **Gemessen**, **Geschlossen** und **Offen** — auch wenn «Offen» leer ist; dann steht dort explizit «keine offenen Punkte»
- [ ] Jedes Finding trennt Beleg (`Evidence`) von Schlussfolgerung, und beides von dem, was ungeklärt blieb
- [ ] Kein unerklärter Rest wird mit einer Vermutung geschlossen; Vermutungssprache steht ausschliesslich unter «Geschlossen» oder «Offen»
- [ ] Zu jedem offenen Punkt ist **eine konkrete Frage** formuliert, deren Antwort zwischen den Hypothesen unterscheidet — samt Adressat und Datum, falls gestellt
- [ ] Ein `pass` beruht auf einem positiven Beleg, nicht auf der Abwesenheit eines Negativbelegs; sonst `not_verified`
- [ ] Wird eine frühere Vermutung später widerlegt, wird sie als **korrigiert** festgehalten, nicht stillschweigend ersetzt

## Common Failures

| Anti-Pattern | Risiko |
|---|---|
| «vermutlich X» im Ergebnisteil | Kennzeichnung überlebt die erste Weitergabe nicht |
| Rest weggerundet («im Wesentlichen deckungsgleich») | Differenz wird nie gemessen |
| Leerer `grep` → `pass` | Nicht gesucht und nichts gefunden werden gleichgesetzt |
| Offener Punkt ohne konkrete Frage | Bleibt offen, weil niemand weiss, was zu fragen wäre |
| Widerlegte Vermutung still ersetzt | Die falsche Erklärung überlebt in Zitaten und Folgedokumenten |
| «Offen»-Abschnitt weggelassen, wenn leer | Der Leser kann nicht unterscheiden zwischen «nichts offen» und «nicht betrachtet» |

## Remediation

1. Report und Findings um die drei Abschnitte ergänzen (`templates/audit-report.md`, `templates/finding.md` enthalten sie).
2. Den Report nach Vermutungssprache durchsuchen (Modus 1) und jede Fundstelle einordnen: gehört sie unter «Geschlossen» — dann mit Begründung — oder unter «Offen»?
3. Für jeden offenen Punkt **eine** diskriminierende Frage formulieren. Im Ausgangsfall war das: *«Entsprechen die 12 Treffer 12 verschiedenen Entry-IDs?»* — eine Antwort, eine Runde, Hypothese erledigt. Eine gute Frage ist so gebaut, dass beide möglichen Antworten den Fall entscheiden.
4. `pass`-Status ohne positiven Beleg auf `not_verified` zurückstufen.

## Effort

S — Pro Audit 30–60 Minuten. Der Aufwand liegt im ehrlichen Einordnen, nicht im Schreiben.
