# OPS-009 — Herkunft der Fixture

## Description

Ein handgeschriebener Mock kodiert die Annahme seines Autors. Er kann sie deshalb **prinzipiell** nicht widerlegen: Produktivcode und Fixture stammen aus demselben Kopf, zur selben Stunde, aus derselben Lektüre der Dokumentation. Wo beide irren, irren beide gleich — und die Suite bleibt dauerhaft grün.

Das ist keine Nachlässigkeit, sondern eine Eigenschaft der Konstruktion. Ein Test kann nur widerlegen, was er nicht selbst behauptet hat.

**Wie oft das schon zugeschlagen hat, steht bereits im Katalog:**

| Check | Was der Mock nicht bemerken konnte |
|---|---|
| `DRIFT-004` | dass der Endpoint verschwunden ist — der Mock antwortet weiter |
| `FID-006` | dass die Felder eine Ebene tiefer liegen — der Mock hat sie oben |
| `FID-006` | dass die Kopfzeile ihre Schreibweise gewechselt hat — der Mock trägt die alte |
| `FID-007` | dass eine Zählspalte `1 bis 5` enthält — der Mock schreibt Zahlen hinein |

Drei Checks, vier Fundstücke, **eine** Ursache. Jeder von ihnen sagt «gegen die echte Antwort prüfen», und keiner sagt, woher die Antwort kommt, die im Repo liegt. Der Skill `mcp-data-fidelity` nennt die Regel zweimal; der Katalog nirgends.

**Was dieser Check verlangt und was nicht.** Er verlangt **nicht**, dass Unit-Tests live gehen — `OPS-001` trennt Unit und Live aus guten Gründen, und die bleiben. Er verlangt, dass die Fixture, gegen die die Unit-Tests laufen, einmal von der **Quelle** kam und dass im Repo steht, **wann**. Danach ist sie ein eingefrorener Zeitpunkt statt einer Vermutung, und der Abstand zwischen Aufnahmedatum und heute ist eine lesbare Zahl statt eines Gefühls.

**Warum das Datum und nicht nur die Herkunft.** «Aufgezeichnet» ohne Zeitpunkt ist nach zwei Jahren von «ausgedacht» nicht mehr zu unterscheiden — die Datei sieht gleich aus, und niemand weiss, ob sie den Stand von gestern oder von vor drei Schema-Wechseln zeigt. Das Datum ist das, was aus einer Datei einen Beleg macht.

**Abgrenzung zu `DRIFT-004`.** Der verlangt, dass die Endpoint-**Konstanten** live verifiziert werden. Dieser Check verlangt, dass die **Antwort**, gegen die im Alltag getestet wird, eine Herkunft hat. Ein Server kann `DRIFT-004` erfüllen — der Live-Test läuft nightly und bestätigt die URL — und trotzdem hundert Unit-Tests gegen einen Mock fahren, den niemand je mit der Quelle verglichen hat.

**Abgrenzung zu `OPS-001`.** Der regelt die **Struktur** der Testlandschaft (Unit gemockt, Live gemarkert, CI-Trennung). Er sagt ausdrücklich «Unit-Tests verwenden `respx` für HTTP-Mocking» — und schweigt darüber, womit `respx` antwortet. Dieser Check füllt genau diese Stelle.

`high`: Er ist die gemeinsame Voraussetzung von vier bestehenden Checks. Wer ihn nicht erfüllt, erfüllt die anderen vier nur dem Wortlaut nach.

## Verification

### Modus 1: code_review (gibt es Fixtures, und woher kommen sie?)

```bash
# Wo liegen die Fixtures?
find tests/ -type d \( -name fixtures -o -name cassettes -o -name recorded -o -name data \)

# Trägt irgendeine eine Herkunft?
grep -rliE 'recorded_at|captured_at|fetched_at|aufgezeichnet|Aufnahmedatum|source_url' \
  tests/ 2>/dev/null

# Der Gegenbefund: Antwort-Literale direkt im Testcode.
grep -rnE 'respond\(\s*200\s*,\s*json\s*=\s*\{|\.mock\(.*json=\{|nock\(.*reply\(' \
  tests/ | head -20

# Gibt es ein Werkzeug, das aufzeichnet?
ls scripts/ tools/ 2>/dev/null | grep -iE 'record|capture|refresh|snapshot'
```

Ein Antwort-Literal im Testcode ist der Befund, sobald es einen **externen** Endpunkt darstellen soll. Für einen selbst konstruierten Grenzfall ist es richtig — der Unterschied ist, ob die Fixture behauptet, wie die Quelle antwortet, oder eine Eingabe konstruiert, die sie nie liefern würde.

**Pass-Pattern** — eine Datei je Endpunkt, mit Kopf:

```
tests/fixtures/
├── PROVENANCE.md
├── bista_sek1_2026-08-03.json
└── bista_staatsangehoerigkeit_2026-08-03.json
```

```markdown
<!-- tests/fixtures/PROVENANCE.md -->
| Datei | Endpunkt | Aufgenommen | Womit |
|---|---|---|---|
| `bista_sek1_2026-08-03.json` | `GET {BISTA_API}/sek1` | 2026-08-03 | `scripts/record_fixtures.py sek1` |
| `bista_staatsangehoerigkeit_2026-08-03.json` | `GET {BISTA_API}/staatsangehoerigkeit` | 2026-08-03 | `scripts/record_fixtures.py staatsangehoerigkeit` |

Neu aufnehmen: `python scripts/record_fixtures.py --all`. Die Aufnahme geht
gegen die echte Quelle und ersetzt die Datei samt Datum im Namen.
```

Trägt das Format keinen Platz für einen Kommentar (JSON, CSV), steht die Herkunft in `PROVENANCE.md`; trägt es einen, darf sie auch in der Datei stehen. Was nicht geht, ist beides nicht.

Das Aufzeichnungsskript ist der Teil, der die Regel am Leben hält — eine Fixture, die man nur von Hand erneuern kann, wird nicht erneuert:

```python
# scripts/record_fixtures.py
async def record(name: str) -> None:
    """Holt die echte Antwort und legt sie samt Aufnahmedatum ab."""
    resp = await httpx.AsyncClient().get(ENDPOINTS[name])
    resp.raise_for_status()
    stamp = datetime.now(UTC).date().isoformat()
    (FIXTURES / f"{name}_{stamp}.json").write_text(resp.text, encoding="utf-8")
```

**Fail-Pattern:**

```python
FIXTURE = {"servers": [{"name": "x", "version": "1.0"}]}   # aus dem Kopf des Autors
respx.get(URL).mock(return_value=httpx.Response(200, json=FIXTURE))
```

### Modus 2: documentation_check (Alter und Erneuerungsweg)

```bash
# Wie alt ist die älteste Fixture — gemessen, nicht geschätzt?
grep -rhoE '[0-9]{4}-[0-9]{2}-[0-9]{2}' tests/fixtures/ | sort | head -1

# Steht der Erneuerungsweg im Repo?
grep -rniE 'record_fixtures|fixtures neu aufnehmen|refresh.*fixture' \
  README*.md CONTRIBUTING*.md scripts/ 2>/dev/null
```

Ein Alter ist **kein** Befund — eine Fixture darf alt sein, solange bekannt ist, wie alt. Befund ist ein fehlendes Datum und ein fehlender Weg, sie zu erneuern.

### Modus 3: runtime_test (die Gegenprobe, ohne die der Check nichts wert ist)

Die Aufzeichnung belegt für sich noch nicht, dass die Fixture die Quelle von heute abbildet. Der Test, der beides verbindet:

```python
@pytest.mark.live
async def test_the_recorded_fixture_still_matches_the_source():
    """Hält die Aufnahme gegen die Quelle — auf der Ebene, die der Code liest."""
    live = await _fetch(ENDPOINT)
    recorded = json.loads(FIXTURE_PATH.read_text(encoding="utf-8"))
    assert set(_READ_FIELDS) <= set(live[0]), sorted(live[0])
    assert set(recorded[0]) == set(live[0]), (
        f"Fixture vom {FIXTURE_DATE} kennt {sorted(set(recorded[0]) - set(live[0]))}, "
        f"die Quelle kennt {sorted(set(live[0]) - set(recorded[0]))} — neu aufnehmen"
    )


def test_a_handwritten_fixture_would_be_caught():
    """Gegenprobe: eine erfundene Antwort danebenhalten und zeigen, dass sie auffällt."""
    invented = [{"name": "x"}]           # plausibel, nie von der Quelle gesehen
    assert set(invented[0]) != set(json.loads(FIXTURE_PATH.read_text())[0])
```

Läuft die Live-Suite gar nicht, ist der Ausgang `todo`, nicht `pass` (§2.6). Dass sie **ausgeführt** wird, prüft `DRIFT-005`.

## Pass Criteria

- [ ] Für **jeden** externen Endpunkt liegt mindestens eine Fixture vor, die von der echten Quelle stammt
- [ ] Jede solche Fixture trägt ein **Aufnahmedatum** — im Dateinamen, im Dateikopf oder in einer `PROVENANCE`-Datei daneben
- [ ] Die Herkunft nennt den **Endpunkt**, gegen den aufgenommen wurde, nicht nur «die API»
- [ ] Es gibt einen dokumentierten Weg, die Aufnahme zu **wiederholen** — ein Skript oder ein Befehl, nicht eine Erinnerung
- [ ] Antwort-Literale im Testcode stellen keinen externen Endpunkt dar; wo sie stehen, konstruieren sie einen Grenzfall, den die Quelle nicht liefert
- [ ] Ein Live-Test hält mindestens eine Aufnahme gegen die Quelle — auf der Ebene der Felder, die der Code liest
- [ ] **Gegenprobe:** Eine erfundene Antwort ist einmal danebengehalten worden und hat sich von der Aufnahme unterschieden. Ohne sie belegt der Vergleich nur, dass zwei Dateien gleich sind

## Common Failures

| Anti-Pattern | Risiko |
|---|---|
| Fixture als Literal im Testcode | Kodiert die Annahme des Autors und bestätigt sie dauerhaft |
| Aufgezeichnet, aber ohne Datum | Nach zwei Jahren von «ausgedacht» nicht mehr zu unterscheiden |
| Ein Aufnahmedatum für das ganze Verzeichnis | Der Endpunkt, der seither gewechselt hat, verschwindet im Mittelwert |
| Aufzeichnung nur von Hand möglich | Wird einmal gemacht und nie wiederholt |
| Fixture aus der API-Dokumentation abgeschrieben | Dokumentation ist auch nur eine Behauptung — und altert schneller als der Endpunkt |
| Nur der Happy Path aufgezeichnet | Der Fehlerpfad bleibt erfunden, und `FID-003` prüft genau ihn |
| Aufnahme mit Zugangsdaten oder Personendaten abgelegt | Die Fixture wandert ins Repo (`SEC-013`, `CH-002`) |
| Live-Vergleich ohne Gegenprobe | Belegt, dass zwei Dateien gleich sind, nicht dass eine von der Quelle kommt |

## Remediation

1. Ein Aufzeichnungsskript schreiben (`scripts/record_fixtures.py`), das je Endpunkt die echte Antwort holt und mit Datum ablegt.
2. Einmal gegen alle Endpunkte laufen lassen. Die Diffs gegen die bisherigen Handmocks sind der eigentliche Ertrag — sie sind die Liste der Annahmen, die nie stimmten.
3. `PROVENANCE.md` anlegen: Datei, Endpunkt, Datum, Befehl.
4. Vor dem Commit prüfen, was aufgezeichnet wurde — Zugangsdaten und Personendaten gehören nicht ins Repo (`SEC-013`, `CH-002`). Eine Aufnahme wird redigiert, nicht erfunden; was entfernt wurde, gehört in den Dateikopf.
5. Den Weg im `CONTRIBUTING` nennen, damit die nächste Person nicht wieder von Hand schreibt.
6. Gegenprobe: eine erfundene Antwort danebenhalten und zeigen, dass der Vergleich sie verwirft.

## Effort

M — Pro Server 1–2 Tage. Das Skript ist schnell; die Zeit geht in die Diffs aus Schritt 2 und in das Redigieren aus Schritt 4.
