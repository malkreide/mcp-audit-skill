# SEC-027 — Custom Header aus Tool-Parametern

## Description

Dasselbe SEP, das die Pflichtheader einführt (`SCALE-008`), bringt eine zweite Fähigkeit mit: **`x-mcp-header`** erlaubt es, HTTP-Header aus Tool-Parametern zu setzen. Praktisch für Korrelations-IDs, Mandantenkennungen oder ein `Accept-Language` je Aufruf.

**Und damit ein Weg, auf dem ein vom Modell erzeugter Wert zu einem HTTP-Header wird.** Der Inhalt eines Tool-Parameters ist nicht vertrauenswürdig: Er entsteht aus einem LLM-Kontext, in dem fremder Text stand — ein Dokument, eine API-Antwort, eine Benutzernachricht. `SEC-018` verlangt Validierung an der Tool-Grenze; dieser Check nennt den Kanal, den `SEC-018` nicht kennt, weil es ihn bis `2026-07-28` nicht gab.

Drei Wirkungen, nach Schwere:

1. **Überschreiben von Auth-Headern.** Ein `Authorization`-Header aus einem Tool-Parameter ersetzt das Service-Account-Token des Servers. Das ist Token-Passthrough (`SEC-002`) durch die Hintertür — und zwar eine, die keine Auth-Konfiguration passiert.
2. **Überschreiben der Pflichtheader.** Ein `Mcp-Name` aus einem Parameter hebt die Übereinstimmungsprüfung aus `SCALE-008` aus ihren Angeln: Gateway und Server entscheiden wieder über verschiedene Anfragen.
3. **Header-Injection.** Ein Wert mit `\r\n` teilt die Anfrage. Wo eine Zwischeninstanz das anders parst als der Server, ist das Request Smuggling.

**Die häufigste Antwort im Portfolio wird «wird nicht verwendet» sein — und die ist zu belegen, nicht anzunehmen.** Die Fähigkeit kann aus dem SDK kommen, ohne dass eine Zeile Servercode sie anfordert. Ein `pass` heisst hier: nachgesehen, dass das SDK sie nicht per Default durchreicht.

## Verification

### Modus 1: automated (wird die Fähigkeit berührt?)

```bash
grep -rniE "x-mcp-header|custom_headers|extra_headers|headers=.*param|passthrough_headers" \
    src/ --include="*.py" --include="*.ts"
```

Und die Gegenrichtung, die der Servercode nicht zeigt:

```bash
SDK=$(python -c 'import mcp,pathlib;print(pathlib.Path(mcp.__file__).parent)')
grep -rn "x-mcp-header" "$SDK" | head
```

Findet der zweite Aufruf etwas, ist die Default-Belegung im SDK zu lesen — nicht anzunehmen. Findet er nichts, gehört die SDK-Version in die Evidenz, sonst gilt der Befund nur für die zufällig installierte.

### Modus 2: code_review (Allow-List und Normalisierung)

**Pass-Pattern:**

```python
# Was hereindarf, wird aufgezählt — nicht, was nicht hereindarf
ALLOWED_PARAM_HEADERS = frozenset({"accept-language", "x-correlation-id"})
_HEADER_VALUE = re.compile(r"\A[\x20-\x7E]{0,256}\Z")   # kein CR, kein LF

def headers_from_params(raw: dict[str, str]) -> dict[str, str]:
    out: dict[str, str] = {}
    for name, value in raw.items():
        key = name.strip().lower()
        if key not in ALLOWED_PARAM_HEADERS:
            raise ToolError(f"Header {name!r} ist nicht zugelassen")
        if not _HEADER_VALUE.fullmatch(value):
            raise ToolError(f"Header {name!r} enthält unzulässige Zeichen")
        out[key] = value
    return out
```

Zwei Details, die eine Deny-List nicht leistet und die deshalb in der Allow-List stecken müssen:

- **Vergleich auf normalisierten Namen.** HTTP-Header sind case-insensitiv; eine Deny-List auf `Authorization` lässt `authorization` durch.
- **Der Wert wird geprüft, nicht nur der Name.** Ein zugelassener Name mit `\r\n` im Wert ist die Injection.

### Modus 3: runtime_test

Drei Aufrufe: ein zugelassener Header kommt an; `Authorization` wird abgelehnt; ein Wert mit `\r\n` wird abgelehnt. Der erste ist Pflicht — sonst belegt die Ablehnung nur, dass die Funktion alles ablehnt.

## Pass Criteria

- [ ] Wird `x-mcp-header` nicht genutzt, ist **belegt**, dass weder Servercode noch SDK-Default sie durchreicht — inklusive SDK-Version
- [ ] Bei Nutzung: eine **Allow-List** zulässiger Header-Namen, keine Deny-List
- [ ] Der Namensvergleich läuft auf kleingeschriebenen, getrimmten Namen
- [ ] `Authorization`, `Cookie`, `Mcp-Method`, `Mcp-Name` und `Host` sind nie zulässig
- [ ] Header-**Werte** werden gegen CR, LF und Steuerzeichen geprüft und in der Länge begrenzt
- [ ] Kein Wert aus einem Tool-Parameter erreicht einen ausgehenden Upstream-Request, ohne dieselbe Prüfung zu durchlaufen
- [ ] **Evidence-Paar:** Tests belegen die Ablehnung von `Authorization` und `\r\n` **und** das Durchkommen eines zugelassenen Headers
- [ ] Ein abgelehnter Header erzeugt einen Execution-Error mit klarer Meldung (`OBS-001`), keinen Stacktrace (`OBS-002`)

## Common Failures

| Anti-Pattern | Konsequenz |
|---|---|
| Deny-List statt Allow-List | Der nächste sicherheitsrelevante Header steht nicht darauf |
| Vergleich auf dem Originalnamen | `authorization` klein geschrieben passiert die Prüfung |
| Nur der Name geprüft | `\r\n` im Wert ist die eigentliche Injection |
| Weiterreichen an den Upstream ohne erneute Prüfung | Server wird zum Werkzeug gegen die Quelle; `SEC-004` |
| «nutzen wir nicht» ohne Blick ins SDK | Die Fähigkeit kommt aus dem Transport, nicht aus dem Servercode |
| Nur Negativtests | Eine durchgehend ablehnende Funktion besteht |

## Remediation

Siehe Pass-Pattern. Wenn die Fähigkeit nicht gebraucht wird — der Normalfall im Portfolio —, ist die Behebung eine Zeile und ein Test:

```python
def test_param_headers_are_not_forwarded(client, upstream):
    client.call("searchDocuments", {"query": "x",
                                    "_headers": {"Authorization": "Bearer attacker"}})
    assert "authorization" not in {k.lower() for k in upstream.last_request.headers}
    assert upstream.last_request.headers["authorization"] == SERVICE_TOKEN
```

Die zweite Zusicherung ist die wichtigere: Sie belegt, dass der *richtige* Header noch da ist. Ohne sie besteht auch ein Server, der gar keine Header mehr sendet.

## Effort

S — Allow-List, Wertprüfung, drei Tests. Für Server ohne Nutzung: ein Beleg und ein Regressionstest.
