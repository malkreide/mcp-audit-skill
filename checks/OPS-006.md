# OPS-006 — Ein Gate ohne Version urteilt jeden Tag anders

## Description

`OPS-005` fragt, ob ein Check gelaufen ist. Dieser Check fragt, ob sein Urteil morgen noch dasselbe wäre — und ob der Nachweis, den man in der Hand hält, überhaupt von dem Werkzeug stammt, das in der CI entscheidet.

Ein Gate ist eine Behauptung über Code, die ein Werkzeug ausspricht. Formatter, Linter und Typechecker sprechen sie versionsabhängig aus: Der Regelsatz wächst, die Vorgaben ändern sich, die Ausgabe wird umformuliert. Solange nur `check` läuft, fällt das kaum auf — neue Regeln kommen meist als Vorschlag. Ein **Formatcheck** dagegen ist binär und lückenlos: Er betrifft jede Zeile jeder Datei, und schon eine geänderte Vorgabe färbt einen ganzen Baum rot, an dem niemand etwas getan hat.

Vier Ausprägungen. Die ersten drei wurden in einem einzigen Rollout über 32 Repos beobachtet — zwei davon als eigene Fehler beim Ausrollen. Die vierte entstand aus dem Schritt danach: dem Versuch, das Gate lokal vorzuziehen.

**Das Gate hat keine Version.** 29 der 32 Repos deklarierten `ruff>=0.4.0` oder ähnlich, ohne obere Grenze. Die CI installiert damit bei jedem Lauf die jeweils neueste Fassung. Solange nur `ruff check` lief, war das erträglich. Ein `ruff format --check` ohne Pin ist etwas anderes: **Die nächste Version, die am Formatter etwas ändert, blockiert portfolioweit den Merge-Pfad** — gleichzeitig, in allen Repos, an unberührtem Code, zu einem Zeitpunkt, den niemand gewählt hat. Wer ein Formatgate einführt, ohne zu pinnen, tauscht eine bekannte Lücke gegen einen Zeitzünder.

Das Gegenargument, ein Pin verzögere Verbesserungen, trifft zu und ist der Punkt: Ein Versionswechsel wird damit zu einem eigenen, datierten Commit mit eigenem Diff, statt zu einem Überraschungsereignis in fremden Pull Requests.

**Der Nachweis stammt aus einer anderen Version als das Gate.** Beim Ausrollen lagen zwei ruff-Binaries im `PATH`: `/root/.local/bin/ruff` (0.15.8) verdeckte `/usr/local/bin/ruff` (0.16.1), und die CI installierte 0.16.1. Derselbe Befehl im selben frischen Klon zählte je nach Binary **17 oder 56 Dateien**. Eine lokal grüne Prüfung belegte damit nichts über die CI — und eine Zahl aus dieser Prüfung führte zu einer falschen Diagnose, die erst zwei Schritte später auffiel.

**Das Urteil wird aus dem Ausgabetext gelesen statt aus dem Exit-Code.** Um zu zählen, wie viele Dateien der Formatter anfassen würde, lag ein `grep -c "^Would reformat"` nahe — die Formulierung von ruff 0.15. Version 0.16 schreibt `unformatted: File would be reformatted`. Das Muster traf nie zu, das Ergebnis war überall sauber `0`, und die daraus abgeleitete Aussage «alle 32 Repos sind bereits formatgerecht» war falsch: Es waren **205 Dateien**. Ein Zählfehler dieser Art ist nicht auffällig, sondern beruhigend — er meldet Null.

Der Exit-Code ist die Schnittstelle, die Werkzeuge stabil halten; der Ausgabetext ist es nicht. Wer auf Text prüft, prüft eine Formulierung.

**Die Version steht an zwei Orten, und nichts bindet sie aneinander.** Ein Pin in der CI löst die erste Ausprägung — und erzeugt beim nächsten Schritt eine neue. Wer den Formatcheck lokal vorzieht, legt einen Pre-Commit-Hook an, und der pinnt dasselbe Werkzeug ein zweites Mal:

```yaml
# .pre-commit-config.yaml        # .github/workflows/lint.yml
rev: v0.15.8                     # pip install ruff==0.15.8
```

Laufen die beiden auseinander, formatiert der Hook nach der einen und die CI prüft nach der anderen Version: **der Hook meldet grün und die CI wird rot** — also genau der Fehlschlag, gegen den der Hook eingeführt wurde, eine Ebene höher. Der Hook ist dabei nicht überflüssig, im Gegenteil: Er installiert das Werkzeug in einer eigenen Umgebung und macht die zweite Ausprägung oben unmöglich. Er kauft das mit einem zweiten Pin.

Abgesichert war das in beiden Repos, in denen es zuerst auftrat, durch einen Kommentar in beiden Dateien, der darum bittet, sie zusammen zu bumpen. **Bitten ist keine Prüfung** — dieselbe Bauart wie `OPS-005`: Es gibt keinen Zeitpunkt, an dem etwas rot wird, wenn niemand den Kommentar liest.

Die Verallgemeinerung gilt über Ruff hinaus: Jede Werkzeugversion, die an zwei Orten steht — CI und Hook, CI und Devcontainer, CI und `Makefile` —, braucht etwas, das die Übereinstimmung erzwingt. Der zweite Ort ist nicht das Problem; der unbewachte Abstand zwischen beiden ist es.

`high`: Die erste Ausprägung legt den Merge-Pfad des ganzen Portfolios lahm, die zweite und dritte erzeugen Nachweise, die nichts belegen und wie Belege aussehen, die vierte lässt ein lokales Gate grün melden, was die CI ablehnt. Das ist dieselbe Klasse wie `OPS-005` — ein Urteil, dem man vertraut, ohne dass es gedeckt ist.

**Adoptionsstufe `advisory`.** Der Check ist neu und trifft absehbar Repos, die noch nicht pinnen. Er meldet, blockiert aber nicht, bis ein Portfolio-Durchlauf zeigt, ob er richtig geschnitten ist — der in `SKILL.md` 2.3 dokumentierte Weg.

## Verification

### Modus 1: config_check (Pin im Gate)

```bash
# Welche Version installiert die CI tatsächlich?
grep -rnE "pip install [^|]*ruff|uv (pip )?install[^|]*ruff|--with ruff|ruff==" .github/workflows/
grep -nE '"(ruff|mypy|black)' pyproject.toml

# Und was heisst «neueste» heute? Weicht das vom Pin ab, ist der Pin real.
pip index versions ruff 2>/dev/null | head -2
```

Ein Formatcheck **und** eine unbegrenzte Range im selben Repo ist der Befund.

**Pass-Pattern** — Pin im Workflow, Begründung daneben, `pyproject.toml` unberührt:

```yaml
      # Pin ruff so an upstream release cannot change the default rule set or
      # formatter and break CI on unrelated, untouched code.
      - name: Install pinned ruff
        run: pip install ruff==0.16.1

      - run: ruff check src/ tests/ scripts/
      - run: ruff format --check src/ tests/ scripts/
```

Für uv-verwaltete Repos ohne Eingriff in die Abhängigkeiten:

```yaml
      - run: uv run --with ruff==0.16.1 ruff format --check src/ tests/ scripts/
```

Den Pin in die CI zu legen statt in `pyproject.toml` ist Absicht: Lokal soll eine neuere Fassung erlaubt bleiben, verbindlich ist die CI.

**Fail-Pattern:**

```yaml
      - run: pip install ruff              # was immer heute neu ist
      - run: ruff format --check src/      # binäres Gate auf beweglichem Grund
```

### Modus 2: runtime_test (Nachweis aus der richtigen Version)

```bash
# Verdeckt eine ältere Installation die, die gemeint ist?
which -a ruff && ruff --version

# Den Pin aus dem Workflow ziehen und exakt damit prüfen
PIN=$(grep -rhoE "ruff==[0-9.]+" .github/workflows/ | head -1 | cut -d= -f3)
echo "Gate verlangt ruff $PIN"
pipx run "ruff==$PIN" format --check src/ tests/ scripts/
```

Weicht die lokale Version vom Pin ab, ist jedes lokale Ergebnis nur ein Indiz.

**Pass-Pattern** — Urteil aus dem Exit-Code, mit ausdrücklichen Zweigen:

```bash
if ruff format --check src/ tests/ scripts/; then
  echo "formatgerecht"
else
  echo "BEFUND: nicht formatgerecht"; exit 1
fi
```

**Fail-Pattern** — Urteil aus einer Formulierung, die die nächste Version ändert:

```bash
n=$(ruff format --check . | grep -c "^Would reformat")   # 0.15-Wortlaut
[ "$n" = 0 ] && echo "alles sauber"                      # unter 0.16 immer wahr
```

Gegenprobe, die den Fehler sofort zeigt: eine bekannt unformatierte Datei durch die Zählung schicken. Meldet sie `0`, misst sie den Wortlaut, nicht den Zustand.

### Modus 3: config_check (Beide Pins nennen dieselbe Version)

```bash
# Der Pin, den die CI installiert
grep -rhoE "ruff==[0-9][^[:space:]\"']*" .github/workflows/ | sort -u

# Der Pin, nach dem der Hook formatiert
sed -n '/ruff-pre-commit/,/hooks:/{s/^[[:space:]]*rev:[[:space:]]*v\{0,1\}\([0-9][^[:space:]]*\)[[:space:]]*$/\1/p;}' \
  .pre-commit-config.yaml
```

Zwei verschiedene Zahlen sind der Befund. **Eine fehlende Zahl ist ebenfalls einer** — dann hat der Vergleich nicht
stattgefunden, und ein Skript, das daraufhin «stimmt überein» meldet, ist der Fehler aus 2.6.

**Pass-Pattern** — ein Schritt in der Pipeline, der beide Stellen gegeneinander hält:

```yaml
      - name: Pin-Sync (Workflow ↔ Pre-Commit)
        run: python scripts/check_tool_pin.py
```

**Fail-Pattern** — die Bitte statt der Prüfung:

```yaml
      # ACHTUNG: diese Version und die `rev` in .pre-commit-config.yaml
      # muessen uebereinstimmen. Beim Anheben beide Stellen aendern.
      - run: pip install ruff==0.15.8
```

Der Kommentar ist richtig und hilft niemandem: Er wirkt nur, solange ihn jemand liest. Er gehört zusätzlich dorthin,
nicht anstelle des Schritts.

**Gegenprobe:** Einen der beiden Pins anheben und den Schritt laufen lassen. Meldet er nichts, prüft er nicht, was er
behauptet — der häufigste Grund ist ein Muster, das die Schreibweise der jeweils anderen Datei nicht trifft.

## Pass Criteria

- [ ] Jedes Repo mit `format --check` (oder einem anderen binären, baumweiten Gate) pinnt die Werkzeugversion an der Stelle, die die CI installiert
- [ ] Der Pin trägt eine Begründung, damit die nächste Bearbeitung ihn nicht als Nachlässigkeit entfernt
- [ ] Ein Versionswechsel ist ein eigener Commit mit eigenem Diff, nicht ein Nebeneffekt eines Upstream-Releases
- [ ] Lokale Nachweise stammen aus derselben Version, die die CI installiert — `which -a` und `--version` geprüft, nicht angenommen
- [ ] Skripte, die ein Werkzeugergebnis auswerten, lesen den **Exit-Code**; Ausgabetext wird höchstens angezeigt, nie als Urteil verwendet
- [ ] Jede Zählung über Werkzeugausgabe ist einmal gegen einen bekannt roten Fall gehalten worden — eine Zählung, die immer Null meldet, sieht wie Erfolg aus
- [ ] Steht die Werkzeugversion an mehr als einer Stelle — CI und Pre-Commit-Hook, CI und Devcontainer, CI und `Makefile` —, prüft ein Schritt der Pipeline, dass alle dieselbe nennen
- [ ] Dieser Schritt behandelt einen **fehlenden** Pin als Befund, nicht als Übereinstimmung
- [ ] Der Schritt ist einmal gegen einen gebauten Vorzustand gehalten worden, in dem genau eine der Stellen angehoben wurde

## Common Failures

| Anti-Pattern | Risiko |
|---|---|
| `format --check` bei unbegrenzter Version-Range | Das nächste Upstream-Release blockiert portfolioweit den Merge-Pfad, an unberührtem Code |
| Pin nur in `pyproject.toml`, CI installiert anders | Der verbindliche Ort ist die CI; alles andere ist eine Empfehlung |
| Zwei Installationen im `PATH`, die ältere verdeckt die neuere | Lokal grün, in der CI rot — und niemand sucht bei der Version |
| `grep` auf Werkzeugausgabe als Zählung | Der Wortlaut ändert sich mit der Version, das Muster trifft nie mehr, das Ergebnis ist beruhigend falsch |
| `cmd \| wc -l` statt Exit-Code | Zählt Zeilen, nicht Zustände; leere Ausgabe und Absturz sind ununterscheidbar |
| Version aus dem Gedächtnis angenommen statt abgefragt | «Neueste» ist ein Datum, keine Eigenschaft |
| Zweiter Pin im Pre-Commit-Hook, nur durch einen Kommentar gebunden | Der Hook formatiert nach der einen, die CI prüft nach der anderen Version — lokal grün, in der CI rot |
| Pin-Vergleich, der einen fehlenden Pin als «gleich» wertet | Die Prüfung verschwindet still in dem Moment, in dem eine Stelle das Pinnen aufgibt |

## Remediation

1. Alle Repos mit binärem Gate auflisten und je Repo feststellen, welche Version die CI **tatsächlich** installiert — nicht, welche in `pyproject.toml` steht.
2. Eine Zielversion festlegen und portfolioweit pinnen, mit Begründung im Kommentar.
3. Vor dem Ausrollen genau mit dieser Version formatieren. Wer mit einer anderen formatiert, produziert einen Diff, den das Gate sofort ablehnt.
4. Jede Auswertung von Werkzeugausgabe auf Exit-Codes umstellen und einmal gegen einen bekannt roten Fall halten.
5. Den Versionswechsel als eigenen, wiederkehrenden Vorgang einplanen — etwa quartalsweise, als ein Commit je Repo.

**Was der Rollout danach mitbringt:** Sobald ein Formatgate steht, prüft die CI eines Pull Requests den *Merge-Commit*, nicht den Branch. Ein offener Pull Request kann deshalb rot werden, ohne dass sich an ihm etwas ändert — es genügt, dass der Zielbranch unformatierten Code aufnimmt. Das ist kein Fehler des Gates, sondern seine Wirkung, und es trifft bevorzugt lange offene Pull Requests. Beim Rollout über 32 Repos passierte es zweimal; die Behebung ist jedes Mal: Basis mergen, formatieren, pushen.

## Effort

S — Pro Repo 10–20 Minuten für den Pin. Teuer ist nur der erste Durchgang, wenn zugleich formatiert werden muss; dann bestimmt die Zahl der Dateien den Aufwand, nicht die Zahl der Repos.
