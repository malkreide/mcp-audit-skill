# SEC-026 — Client-Registrierung: CIMD, Issuer-Bindung, `application_type`

## Description

Drei Änderungen an derselben Stelle, die nur zusammen einen behebbaren Zustand ergeben.

**1. DCR ist deprecated, CIMD ist der Weg (PR #2858).** Die Dynamic Client Registration nach RFC 7591 ist als Registrierungsmechanismus abgekündigt zugunsten von **Client ID Metadata Documents**: Statt sich beim Autorisierungsserver zu registrieren und eine `client_id` zugeteilt zu bekommen, veröffentlicht der Client seine Metadaten unter einer URL, und diese URL **ist** die `client_id`. DCR bleibt für Autorisierungsserver, die CIMD nicht können.

**`beide` als Baseline**, weil CIMD nicht neu ist: Es kam als *empfohlener* Mechanismus schon mit `2025-11-25` (SEP-991). `2026-07-28` dreht nur die Vorzeichen — vorher «CIMD empfohlen», jetzt «DCR abgekündigt». Ein Server, der heute neu auf DCR setzt, baut auf beiden Ständen in die falsche Richtung.

**2. Credentials sind issuer-gebunden (SEP-2352).** Clients **MÜSSEN** persistierte Zugangsdaten nach dem Issuer-Identifier schlüsseln, dürfen sie **NICHT** bei einem anderen Autorisierungsserver wiederverwenden, und müssen sich neu registrieren, wenn der Autorisierungsserver wechselt.

Das ist die Speicher-Seite desselben Angriffs, dessen Netz-Seite `SEC-025` abwehrt. Ein Proxy, der `client_id` und `client_secret` in einer flachen Konfiguration hält, präsentiert sie jedem Autorisierungsserver, mit dem er spricht. Beim ersten zusätzlichen Issuer — oder beim ersten untergeschobenen — gibt er die Zugangsdaten des einen dem anderen preis.

**3. `application_type` bei verbleibender DCR (SEP-837).** Wer DCR weiterhin nutzt, muss `application_type` setzen. Ohne die Angabe defaultet OpenID Connect auf `web`, was `https`-Redirect-URIs ohne Loopback erzwingt — ein nativer Client mit `http://127.0.0.1:…` wird dann bei der Registrierung abgelehnt oder, schlimmer, mit einer Redirect-URI registriert, die er nicht bedienen kann.

## Verification

### Modus 1: automated

```bash
# Registrierungsmechanismus
grep -rniE "register|client_id_metadata|client-id-metadata|cimd|application_type|rfc7591" \
    src/ --include="*.py" --include="*.ts"

# Wie werden Credentials abgelegt?
grep -rniE "client_secret|client_id" src/ --include="*.py" --include="*.ts"
```

Negative Kontrolle: `grep -rn "client_id"` muss im OAuth-Modul etwas finden. Findet es nichts, greift der Pfad nicht, den der Check prüft — Ausgang `not_verified`, nicht `pass`.

### Modus 2: code_review (Form des Speichers)

Die entscheidende Frage ist nicht, *ob* Credentials gespeichert werden, sondern **wonach sie geschlüsselt sind**.

```python
# ANTI-PATTERN — flach, ein Satz Zugangsdaten für alle Issuer
CLIENT_ID = os.environ["OAUTH_CLIENT_ID"]
CLIENT_SECRET = os.environ["OAUTH_CLIENT_SECRET"]

# PASS — der Issuer ist Teil des Schlüssels, nicht Teil der Umgebung
_CREDS: dict[str, ClientCredentials] = {}      # issuer -> credentials

def credentials_for(issuer: str) -> ClientCredentials:
    creds = _CREDS.get(issuer)
    if creds is None:
        raise UnknownIssuerError(
            f"Keine Registrierung für {issuer}. Neu registrieren, "
            f"niemals Zugangsdaten eines anderen Issuers verwenden."
        )
    return creds
```

Der Fehlerpfad gehört dazu: Ein `dict.get()` mit Fallback auf den Default-Eintrag ist derselbe Fehler wie die flache Konfiguration, nur schwerer zu sehen.

### Modus 3: documentation_check

Bei CIMD: Das Metadaten-Dokument ist unter der als `client_id` verwendeten URL erreichbar, per HTTPS, und die dort genannten `redirect_uris` decken sich mit denen, die der Server tatsächlich bedient.

```bash
curl -sS "$CLIENT_ID_URL" | jq '{client_id, redirect_uris, application_type}'
```

## Pass Criteria

- [ ] Neue Registrierungen laufen über CIMD, sofern der Autorisierungsserver es unterstützt
- [ ] Wird DCR genutzt, ist das begründet (Autorisierungsserver kann kein CIMD) und im README festgehalten
- [ ] Bei DCR ist `application_type` explizit gesetzt und passt zum tatsächlichen Client-Typ
- [ ] Persistierte Client-Credentials sind **nach Issuer geschlüsselt** — belegt an der Datenstruktur, nicht an der Absicht
- [ ] Ein unbekannter Issuer führt zu einem Fehler, nicht zu einem Fallback auf vorhandene Zugangsdaten
- [ ] Wechselt der Autorisierungsserver, wird neu registriert; alte Zugangsdaten werden nicht mitgenommen
- [ ] Bei CIMD: Das Metadaten-Dokument ist unter der `client_id`-URL per HTTPS erreichbar und deckt sich mit den bedienten `redirect_uris`
- [ ] Client-Secrets liegen im Secret Manager, nicht in Klartext-Env-Vars (`SEC-013`)
- [ ] **Gegenprobe:** Ein Test fordert Zugangsdaten für einen unbekannten Issuer an und bekommt einen Fehler statt der Default-Zugangsdaten

## Common Failures

| Anti-Pattern | Konsequenz |
|---|---|
| Ein Satz Credentials für alle Issuer | Zugangsdaten des einen Autorisierungsservers gehen an den anderen |
| `_CREDS.get(issuer, DEFAULT)` | Derselbe Fehler, versteckt in einem Default-Argument |
| DCR ohne `application_type` | OIDC defaultet auf `web`; Loopback-Redirect wird abgelehnt |
| Neue Integration auf DCR gebaut | Baut auf einen abgekündigten Mechanismus, auf beiden Baselines |
| CIMD-URL nicht erreichbar oder per `http` | Autorisierungsserver kann die Metadaten nicht prüfen |
| `redirect_uris` im Dokument weiter als die bedienten | Redirect-URI-Verwirrung; erweitert die Angriffsfläche aus `SEC-001` |
| Credentials im Repo oder in Klartext-Env | `SEC-013`, unabhängig von der Issuer-Frage |

## Remediation

```python
# CIMD: die client_id IST die URL des Metadaten-Dokuments
CLIENT_ID = "https://mcp.example.ch/.well-known/oauth-client"

# Registrierung je Issuer, mit dem Issuer als Schlüssel
async def ensure_registered(issuer: str) -> ClientCredentials:
    if (creds := await store.get(issuer)) is not None:
        return creds
    meta = await fetch_as_metadata(issuer)
    if meta.get("client_id_metadata_document_supported"):
        creds = ClientCredentials(client_id=CLIENT_ID, secret=None)   # CIMD
    else:
        creds = await dynamic_register(               # DCR als Rückfallweg
            issuer, application_type="native",        # SEP-837, nie weglassen
            redirect_uris=["http://127.0.0.1:8765/callback"],
        )
    await store.put(issuer, creds)                    # geschlüsselt nach Issuer
    return creds
```

## Effort

M — die Issuer-Schlüsselung ist eine kleine Umstellung mit grosser Reichweite: Jede Stelle, die heute `CLIENT_ID` aus der Umgebung liest, wird zu einem Aufruf mit Issuer-Argument. L, wenn zusätzlich ein CIMD-Dokument veröffentlicht und betrieben werden muss.
