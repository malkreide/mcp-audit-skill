# FID-004 — Vollständige Parameter-Sets

## Description

Die feinere Ausprägung von FID-001. Sendet ein Server eine **Teilmenge** einer zusammengehörigen Parameter-Gruppe, behalten die nicht gesendeten Mitglieder ihren serverseitigen Default. Das Ergebnis ist ein Parameter, der aussieht, als würde er steuern, tatsächlich aber nur addieren kann — nie einschränken.

Der Portfolio-Fall: `termdat-mcp` bot ein `fields`-Argument an und übersetzte es in `Field.Terminus=true`. Die API setzt `Terminus`, `Name`, `Abbreviation` und `Phraseology` per Default auf `true`. Das Argument war damit ein No-op. Empirisch belegt an einem Referenzbegriff:

| Gesendet | Treffer |
|---|---:|
| kein `Field.*` | 29 |
| `Field.Terminus=true` | 29 |
| `Field.Terminus=false`, `Field.Name=true` | 10 |

Die dritte Zeile beweist, dass Einschränken möglich ist — aber nur durch **explizites `false`**. Ein Argument, dessen Wirkung sich nicht messen lässt, ist schlimmer als kein Argument: Der Aufrufer glaubt, er habe eingeschränkt, und trifft Entscheidungen auf dieser Annahme.

Betroffen sind alle Konstruktionen, bei denen mehrere Parameter gemeinsam einen Zustandsraum aufspannen: boolesche Feld-Flags (`Field.*`, `include_*`, `with_*`), Facetten-Selektionen, Sichtbarkeits-Schalter, Format-Optionen. Erkennungsmerkmal in der Spec: mehrere Parameter mit gemeinsamem Präfix, jeder mit eigenem dokumentiertem Default.

`medium`, weil der Schaden begrenzt bleibt — die Suche ist zu breit, nicht zu eng, und liefert damit zu viel statt zu wenig. Die Behebung ist trivial, die Fehlannahme jedoch zäh.

## Verification

### Modus 1: code_review (Sendet der Server alle Mitglieder?)

```bash
# Baut der Code Parameter aus einer Auswahl statt aus der Gesamtmenge?
grep -rn "for .* in fields\|for .* in selected\|if .* in requested" src/ --include=*.py

# Gegenprobe: kennt der Code die vollständige Gruppe überhaupt?
grep -rn "SEARCH_FIELDS\|ALL_FIELDS\|_FLAGS\b" src/ --include=*.py
```

**Pass-Pattern:**

```python
# Jedes Flag der Gruppe wird explizit gesetzt — nur so kann `fields` verengen.
requested = set(fields)
for field in SEARCH_FIELDS:
    params[f"Field.{field}"] = "true" if field in requested else "false"
```

**Fail-Pattern:**

```python
# Nicht gesendete Flags behalten ihren Server-Default (hier: true).
for field in fields:
    params[f"Field.{field}"] = "true"
```

### Modus 2: runtime_test (Wirkungsnachweis)

Ein Argument, dessen Wirkung nicht messbar ist, gilt als nicht vorhanden. Drei Calls, ein Referenzbegriff mit vielen Treffern:

```python
@pytest.mark.live
async def test_fields_can_narrow_the_search():
    """Nicht gesendete Field.*-Flags stehen upstream auf true — Verengen muss verengen."""
    broad, _ = await client.search("Steuer", "DE", max_results=1000)
    narrow, _ = await client.search("Steuer", "DE", fields=("Abbreviation",), max_results=1000)
    assert len(narrow) < len(broad)
```

## Pass Criteria

- [ ] Der Code kennt die vollständige Parameter-Gruppe als Konstante, nicht nur die jeweils angeforderte Teilmenge
- [ ] Jedes Mitglied der Gruppe wird bei jedem Request explizit gesetzt (`true` **oder** `false`)
- [ ] Ein Live-Test belegt, dass die Einschränkung messbar wirkt
- [ ] Der Default-Wert des Arguments entspricht dem tatsächlich gewünschten Set, nicht dem zufälligen API-Default
- [ ] Die Tool-Description nennt das Default-Set explizit, statt es als «alle» oder «Standard» zu umschreiben

## Common Failures

| Anti-Pattern | Risiko |
|---|---|
| Nur angeforderte Flags auf `true` setzen | Argument kann nur erweitern, nie verengen — stiller No-op |
| Default-Wert eines `fields`-Arguments aus der Spec übernehmen | Übernimmt den API-Default statt den fachlich richtigen |
| Wirkung nie gemessen | Niemand merkt, dass das Argument nichts tut |
| Description sagt «Teilmenge von …» ohne Default zu nennen | Aufrufer nimmt an, das Weglassen bedeute «alle» |
| Verengung nur im Client-Code nachgebildet (Post-Filter) | Upstream liefert weiterhin zu viel; Limits/Pagination greifen falsch |

## Remediation

```diff
- for field in fields:
-     params[f"Field.{field}"] = "true"
+ # Jedes Flag explizit. Nicht gesendete Flags behalten ihren API-Default
+ # (Terminus/Name/Abbreviation/Phraseology = true), womit `fields` die Suche
+ # nur erweitern, aber nie verengen könnte.
+ requested = set(fields)
+ for field in SEARCH_FIELDS:
+     params[f"Field.{field}"] = "true" if field in requested else "false"
```
