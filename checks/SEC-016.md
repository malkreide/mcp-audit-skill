# SEC-016 — 0.0.0.0-Binding-Prevention (NeighborJack)

## Description

Die empirische Untersuchung von 2025 ergab: ein erheblicher Teil der OSS-MCP-Server bindet ihren HTTP-Listener an `0.0.0.0` (alle Interfaces) und vertraut implizit darauf, dass Firewall-Regeln den Zugang beschränken. Auf einem Entwickler-Laptop in einem öffentlichen WLAN, einem Co-Working-Space oder einer Konferenz wird der lokale MCP-Server damit für **alle** Geräte im selben Subnetz erreichbar.

**Angriff (NeighborJack):**

1. Entwickler startet lokalen MCP-Server für Tests, gebunden an `0.0.0.0:8080`
2. Server läuft mit User-Privilegien, oft mit Zugriff auf Filesystem, API-Keys, lokale Dev-Datenbanken
3. Angreifer im selben Netz scannt mit `nmap -p 8080 192.168.0.0/24`
4. Findet offenen Port, sendet `tools/list`-Request, erhält Tool-Inventar
5. Ruft destruktive Tools auf: liest Files, exfiltriert API-Keys, löscht Daten

**Warum so häufig:** FastMCP, Express, FastAPI haben in vielen Tutorials `host="0.0.0.0"` als Default. Entwickler kopieren das, ohne über Implikationen nachzudenken. In Container-Kontexten ist `0.0.0.0` korrekt (Container-Netzwerk-Isolation), aber für lokale Entwicklung katastrophal.

**Damit ist der Container-Fall aber nicht erledigt, sondern nur verschoben.** Ein Bind auf `0.0.0.0` beantwortet die Frage «wer darf mich erreichen» nicht mehr über das Interface — sie muss dann auf der Ebene der eingehenden Anfrage gestellt werden: unter welchem Hostnamen der Server angesprochen werden darf. Dafür braucht es eine eigene Prüfung, die dieser Check nicht leistet: **`SEC-024`** (Inbound Host/Origin-Allow-List).

**Der `host`-Wert ist unter dem 2.x-SDK mehr als die Bind-Adresse.** Er ist zugleich die Saat, aus der das SDK seine **eingehende** Host-Allow-List ableitet. `sse_app()` bzw. `streamable_http_app()` tragen `host: str = "127.0.0.1"` als Default; liegt der Wert in `("127.0.0.1", "localhost", "::1")` und ist keine explizite `TransportSecuritySettings` gesetzt, schaltet das SDK den DNS-Rebinding-Schutz automatisch ein — mit einer Allow-List, die genau diese drei Namen enthält.

Daraus folgt eine Falle, die erst im Deployment auffällt: Wird der konfigurierte `host` dem App-Builder **nicht durchgereicht**, greift dessen Default `127.0.0.1`, der Schutz aktiviert sich mit der Localhost-Allow-List — und der Server, der auf `0.0.0.0` lauscht und unter einem echten Hostnamen angesprochen wird, beantwortet **jede** Anfrage mit `HTTP 421 Invalid Host header`. Der Prozess läuft, der Port ist offen, der Health-Check kann grün sein, und trotzdem kommt kein einziger Client durch.

## Verification

### Modus 1: automated (Code-Suche nach Binding)

```bash
# Python — FastMCP, FastAPI, Uvicorn, Hypercorn
grep -rE 'host\s*=\s*["\x27]0\.0\.0\.0|host\s*=\s*["\x27]\*' src/

# TypeScript / Node — Express, Fastify
grep -rE 'listen\([^,)]*,\s*["\x27]0\.0\.0\.0' src/

# Auch in Konfigurationsdateien
grep -rE '0\.0\.0\.0' . --include="*.toml" --include="*.yaml" --include="*.json" --include="*.env*"
```

### Modus 2: code_review (Deployment-Differenzierung)

Der korrekte Pattern unterscheidet **Container** (wo `0.0.0.0` nötig ist) von **lokal** (wo `127.0.0.1` zwingend).

**Pass-Pattern (Python):**

```python
import os
from mcp.server.mcpserver import MCPServer

mcp = MCPServer("zurich-opendata")

if __name__ == "__main__":
    transport = os.environ.get("MCP_TRANSPORT", "stdio")
    if transport == "stdio":
        mcp.run(transport="stdio")  # kein Network-Binding
    elif transport == "sse":
        # Für lokal: 127.0.0.1, für Container: explizites ENV
        host = os.environ.get("MCP_HOST", "127.0.0.1")
        port = int(os.environ.get("MCP_PORT", "8000"))
        mcp.run(transport="sse", host=host, port=port)
```

**Fail-Pattern (veraltete 1.x-API):**

```python
from fastmcp import FastMCP           # 1.x-Pfad

mcp = FastMCP("zurich-opendata")
mcp.settings.host = host              # ValueError: "Settings" object has no field "host"
mcp.settings.port = port
mcp.run(transport="sse")
```

Unter `mcp` 2.x trägt `Settings` weder `host` noch `port` — das Objekt beschreibt Debug, Log-Level, Duplikat-Warnungen, Dependencies, Lifespan und Auth, sonst nichts. Die Zuweisung schlägt beim Start fehl (`ValueError`, weil pydantic ein unbekanntes Feld ablehnt; ein *lesender* Zugriff wirft `AttributeError`). Der Server kommt auf HTTP-Transport gar nicht erst hoch. Bind-Adresse und Port gehören als Kwargs an `run()`.

Der Unterschied zwischen Pass und Fail liegt beim korrigierten Muster also **nicht** mehr in der API-Form, sondern nur noch darin, dass `host` von aussen gesetzt werden kann, auf Loopback vorbelegt ist und als Kwarg am Listener ankommt. Ob der Wert aus `os.environ` oder aus einem `argparse`-Flag stammt, ist für den Check gleichgültig — beide Formen sind im Portfolio in Gebrauch.

**Pass-Pattern (Dockerfile mit ENV-Override):**

```dockerfile
FROM python:3.11-slim
COPY . /app
WORKDIR /app
RUN pip install --no-cache-dir -e .

# Container muss an 0.0.0.0 binden, sonst kein Netzwerk-Zugriff
# aber explizit, nicht als Default im Code
ENV MCP_TRANSPORT=sse
ENV MCP_HOST=0.0.0.0
ENV MCP_PORT=8000

CMD ["python", "-m", "zurich_opendata_mcp"]
```

**Fail-Pattern:**

```python
# FAIL: 0.0.0.0 als Code-Default
mcp.run(transport="sse", host="0.0.0.0", port=8000)

# FAIL: ohne Differenzierung lokal/container
app.listen(8000, "0.0.0.0", () => console.log("ready"));
```

### Modus 3: runtime_test (das Startlog nennt die tatsächlich gebundene Adresse)

Die Modi 1 und 2 zeigen, dass es eine Konfigurationsfläche **gibt**. Sie zeigen nicht, dass der gesetzte Wert dort **ankommt**, wo der Listener gebaut wird — und genau das ist der Fehler, der sich im Code nicht sehen lässt: Ein `--host`, das nur den Parser erreicht, ein `MCP_HOST`, das an `run()` geht, aber nicht an den zweiten App-Pfad daneben, eine `uvicorn --factory`, die ohne Argumente aufgerufen wird. In jedem dieser Fälle ist die Option vorhanden, dokumentiert, getestet — und wirkungslos.

Der belastbare Beleg steht im Startlog. ASGI-Server nennen die Adresse, die sie tatsächlich gebunden haben, von sich aus:

```bash
# Default — ohne jede Konfiguration
<start-kommando> 2>&1 | grep -m1 "Uvicorn running on"
# Erwartet: Uvicorn running on http://127.0.0.1:8000

# Mit gesetztem Wert — Mechanismus egal, hier beide Formen
MCP_HOST=0.0.0.0 <start-kommando> 2>&1 | grep -m1 "Uvicorn running on"
<start-kommando> --host 0.0.0.0     2>&1 | grep -m1 "Uvicorn running on"
# Erwartet: Uvicorn running on http://0.0.0.0:8000
```

**Pass:** Beide Läufe nennen die Adresse, die gesetzt wurde — der Default-Lauf Loopback, der konfigurierte Lauf den konfigurierten Wert.

**Der Default-Lauf allein genügt nicht.** Er bestätigt nur, dass irgendwo `127.0.0.1` steht; ein Server, der die Option vollständig ignoriert, besteht ihn ebenfalls und sieht dabei besonders sicher aus. Erst der zweite Lauf trennt «konfigurierbar» von «hat eine Option, die nichts tut» — es ist dasselbe Argument wie bei der Kontrollprobe in `SEC-024` Modus 2.

Nutzt der Server keinen ASGI-Server mit eigener Startzeile, tut es jede Beobachtung von aussen — `ss -ltnp | grep <port>` auf dem Host oder ein Verbindungsversuch von einem zweiten Interface. Was nicht zählt, ist eine Logzeile, die der Server aus seiner **eigenen Konfigurationsvariablen** schreibt: Die sagt, was er binden wollte, nicht was er gebunden hat, und wäre in genau dem Fehlerfall grün, den dieser Modus finden soll.

### Modus 4: runtime_test (Port-Erreichbarkeit von extern)

Auf dem Dev-Laptop:

```bash
# Server starten
python -m my_mcp_server &

# Aus dem selben Netz prüfen — vom anderen Gerät
LOCAL_IP=$(ipconfig getifaddr en0)  # macOS / hostname -I auf Linux
nmap -p 8000 $LOCAL_IP
# Erwartet: 8000/tcp closed (oder filtered)
# Fail: 8000/tcp open
```

## Pass Criteria

- [ ] Im Code ist **kein** `0.0.0.0`-Binding als Default hardcoded
- [ ] Die Bind-Adresse ist **konfigurierbar** — Environment-Variable *oder* CLI-Flag; der Mechanismus ist frei
- [ ] Der Default ist **Loopback** (`127.0.0.1`)
- [ ] Der gesetzte Wert **erreicht den Listener**: er wird an *jeden* Pfad durchgereicht, der die App oder den Server baut, und ein Lauf mit gesetztem Wert zeigt ihn im Startlog (Modus 3)
- [ ] `0.0.0.0` steht **explizit in der Deployment-Konfiguration** — Dockerfile, `railway.toml`, Compose-File oder Start-Kommando —, nicht im Code
- [ ] README erklärt die Differenzierung lokal/container
- [ ] Ein Bind ausserhalb Loopback ist **nicht still**: Wenn keine eingehende Host-Allow-List ihn kompensiert, sagt eine Startwarnung, dass der Server jetzt im Netz steht

### Warum die Kriterien die Eigenschaft nennen und nicht den Mechanismus

Bis v1.4.x verlangte Kriterium 2 wörtlich «via **Environment-Variable**». Das misst die Bauform statt der Sache. `zurich-opendata-mcp` löst dieselbe Aufgabe mit `--host` und Default `127.0.0.1` — Absicht vollständig erfüllt, Kriterium wörtlich verfehlt. Ein Check, der so gelesen wird, erzeugt ein Finding gegen eine korrekte Implementierung und lädt zur Gegenrichtung ein: eine `MCP_HOST`-Variable nachzurüsten, die niemand liest, damit die Zeile grün wird.

**Der Mechanismus ist nicht der Punkt — das Durchreichen ist es.** Vor `0.7.0` hatte derselbe Server gar keine Konfigurationsfläche: `mcp.run(transport="streamable-http", port=…)` ohne `host=`, uvicorn band immer `127.0.0.1`, und es gab kein Flag, das daran etwas geändert hätte. Ein Kriterium der Form «es existiert eine Env-Var» hätte diesen Zustand angezeigt, aber den Folgefehler nicht: dass eine vorhandene Option den Listener nicht erreicht. Deshalb steht die Wirkung im Kriterium und wird in Modus 3 gemessen, nicht die Herkunft des Wertes.

### Abgrenzung der Startwarnung gegen `SEC-024`

Kriterium 7 war bis v1.4.x als «Optional» geführt. Es ist keines: Alle drei Portfolio-Server, aus denen die Belege stammen, warnen beim Nicht-Loopback-Bind. Was sie **nicht** tun, ist die Container-Detection, die hier früher als Auslöser stand — die ist in keinem einzigen implementiert. Ausgelöst wird bei allen dreien durch die **fehlende Allow-List**, und deshalb ist das Kriterium so formuliert.

Damit kann **dieselbe Logzeile** zwei Checks bedienen, und die Frage, ob das eine Doppelung ist, gehört beantwortet: Nein, aber knapp. `SEC-024` fragt, ob die *Abwesenheit der Allow-List* angesagt wird — Subjekt ist die Allow-List. Hier ist das Subjekt die **Exposition**: dass der Server das Loopback verlassen hat. Zwei Server können deshalb hier bestehen und dort durchfallen (`0.0.0.0` mit Allow-List, kein Wort im Log) und umgekehrt. Wer die Zeile entfernt, verletzt beide — das ist kein Doppelbefund, sondern eine Ursache mit zwei Wirkungen.

Der vollere Fall ist trotzdem besser und in `bag-health-mcp` gebaut: Warnung ohne Allow-List, `INFO` **mit** Allow-List. Dann ist der Bind nie still, auch nicht im sauber konfigurierten Deployment. Gefordert ist er nicht — wer die Allow-List setzt, hat die Exposition erkennbar entschieden.

## Common Failures

| Pattern | Risiko |
|---|---|
| `host="0.0.0.0"` als Code-Default | NeighborJack auf Dev-Laptop |
| `--host 0.0.0.0` als Default-CLI-Arg | gleiche Klasse |
| Docker-Compose mit `ports: - "8000:8000"` ohne Bind-Adresse | Container-Port wird auf alle Interfaces des Hosts gebunden |
| Tutorial-Code 1:1 übernommen | FastAPI-Tutorial nutzt `0.0.0.0` ohne Disclaimer |
| Gar keine Konfigurationsfläche — `run()` ohne `host=` | Loopback ist erzwungen statt gewählt; der Server kann nicht deployed werden, und niemand merkt es bis zum ersten Container |
| Option vorhanden, erreicht den Listener nicht | Sieht in Code-Review und Tests korrekt aus, bindet aber den Default. Nur Modus 3 findet es |
| Wert nur an `run()` durchgereicht, nicht an den zweiten App-Pfad | Der Schutz hängt davon ab, welcher Zweig zufällig greift — vgl. `ARCH-013` |
| Nur der Default-Lauf im Startlog geprüft | Ein Server, der die Option ignoriert, besteht diesen Test und wirkt dabei besonders sicher |
| Logzeile aus der eigenen Konfigurationsvariablen statt vom Server | Sagt, was gebunden werden sollte, nicht was gebunden wurde — grün in genau dem Fehlerfall |
| Auditor wertet ein CLI-Flag als Verstoss, weil keine Env-Var da ist | Finding gegen eine korrekte Implementierung; provoziert eine Variable, die niemand liest |

## Remediation

### Schritt 1: Code-Default auf 127.0.0.1 ändern

Der Mechanismus ist frei. Die Env-Var-Form unten ist eine von zwei gebräuchlichen; ein `argparse`-Flag mit `default="127.0.0.1"` erfüllt dasselbe Kriterium, solange der Wert dieselbe Strecke zurücklegt:

```diff
  if __name__ == "__main__":
      transport = os.environ.get("MCP_TRANSPORT", "stdio")
      if transport == "sse":
-         mcp.run(transport="sse", host="0.0.0.0", port=8000)
+         host = os.environ.get("MCP_HOST", "127.0.0.1")
+         port = int(os.environ.get("MCP_PORT", "8000"))
+         mcp.run(transport="sse", host=host, port=port)
```

`host` und `port` gehen als Kwargs an `run()`. Der Umweg über `mcp.settings.host = …` stammt aus dem 1.x-SDK und scheitert unter 2.x beim Start — siehe das Fail-Pattern in Modus 2.

Wer eine eigene App baut, statt `run()` zu benutzen, muss den Wert **auch dort** durchreichen: `mcp.sse_app(host=host)` bzw. `mcp.streamable_http_app(host=host)`. Ohne das greift der Default `127.0.0.1`, der Server zieht sich die Localhost-Allow-List und antwortet im Container mit `HTTP 421`.

### Schritt 2: Container-Override im Dockerfile

```dockerfile
ENV MCP_HOST=0.0.0.0
```

### Schritt 3: Docker-Compose Bind-Adresse

```yaml
# docker-compose.yml
services:
  mcp:
    image: malkreide/zurich-opendata-mcp
    ports:
-     - "8000:8000"           # bindet an alle Interfaces
+     - "127.0.0.1:8000:8000" # nur lokal erreichbar
```

### Schritt 4: Der Bind ausserhalb Loopback darf nicht still sein

Die Form, die sich im Portfolio durchgesetzt hat, hängt die Warnung an die **fehlende Allow-List**, nicht an eine Container-Heuristik — der Zustand, der wirklich gefährlich ist, ist «im Netz und niemand prüft den `Host`», und der ist ohne Raten feststellbar:

```python
LOOPBACK = ("127.0.0.1", "localhost", "::1")

if host not in LOOPBACK and not allowed_hosts:
    logger.warning(
        "binding HTTP server to non-loopback host %s with no MCP_ALLOWED_HOSTS — "
        "Host/Origin validation is off and left to whatever fronts this server; "
        "set MCP_ALLOWED_HOSTS to the names it is reachable under",
        host,
    )
elif host not in LOOPBACK:
    # Nicht gefordert, aber besser: der Bind ist auch im sauber
    # konfigurierten Fall im Log sichtbar.
    logger.info("binding HTTP server to non-loopback host %s with a Host "
                "allow-list of %s", host, allowed_hosts)
```

Eine **Container-Detection** (`/.dockerenv`, `KUBERNETES_SERVICE_HOST`, `RAILWAY_PROJECT_ID`) ist als zusätzlicher Auslöser möglich, aber nicht verlangt und im Portfolio nirgends gebaut. Sie rät, wo die Allow-List-Prüfung weiss: Ein Container ohne Allow-List ist genauso ungeschützt wie ein Laptop, und ein Laptop mit Allow-List ist es nicht.

### Schritt 5: README-Dokumentation

```markdown
## Network Binding

By default, this server binds to `127.0.0.1` (localhost only).

For production deployment in Docker/Kubernetes, set `MCP_HOST=0.0.0.0`.
**Never** use `0.0.0.0` outside container contexts — it exposes the server
to your local network (NeighborJack risk).
```
