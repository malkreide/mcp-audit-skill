# SEC-025 — `iss`-Validierung nach RFC 9207

## Description

RFC 9207 («OAuth 2.0 Authorization Server Issuer Identification») ergänzt die Authorization-Response um einen `iss`-Parameter. `2026-07-28` macht daraus eine geteilte Pflicht:

> Authorization servers **SHOULD** include the `iss` parameter in authorization responses; MCP clients **MUST** validate a present `iss` against the recorded issuer before redeeming the authorization code.

**Warum das einen MCP-*Server* betrifft.** Ein Server mit `auth_model: "OAuth-Proxy"` ist gegenüber dem Upstream-Autorisierungsserver selbst ein OAuth-Client. Die MUSS-Pflicht trifft ihn in dieser Rolle — sie steht unter «clients», gemeint ist die einlösende Partei.

**Der Angriff, den RFC 9207 schliesst (Mix-Up).** Der Proxy spricht mit mehr als einem Autorisierungsserver, oder ein Angreifer bringt ihn dazu, einen Flow bei einem von ihm kontrollierten zu beginnen. Der Angreifer fängt einen Code ab, der bei Server A ausgestellt wurde, und leitet ihn auf den Callback um, der zu Server B gehört. Ohne `iss` sieht der Proxy nur «ein Code, ein passender `state`» — und löst ihn beim falschen Server ein, mit den Zugangsdaten, die er dort hat.

**Was den Check von `SEC-002` und `SEC-010` unterscheidet.** `SEC-002` prüft die `aud` des *empfangenen* Tokens: Ist dieses Token für mich? `SEC-010` prüft den `state`: Gehört diese Rückkehr zu meinem Flow? Beide beantworten nicht die dritte Frage — **von wem kommt dieser Code**. Der `state` überlebt den Mix-up, weil der Proxy ihn selbst gesetzt hat; er sagt nur, dass die Runde seine ist, nicht, wer sie beantwortet hat.

**Die «present»-Klausel ist die Falle.** Die Pflicht gilt für einen *vorhandenen* `iss`. Ein Proxy, der nur validiert, wenn der Parameter da ist, und sonst weitermacht, erfüllt den Buchstaben — und lässt sich angreifen, indem der Parameter weggelassen wird. Deshalb verlangt dieser Check zusätzlich, dass ein **fehlender** `iss` bei einem Autorisierungsserver, der ihn ausstellt, ebenfalls abgelehnt wird. Was der Autorisierungsserver kann, ist bekannt: Es steht in seinen Metadaten (`authorization_response_iss_parameter_supported`).

## Verification

### Modus 1: automated

```bash
grep -rniE "\biss\b|issuer|9207|authorization_response_iss" src/ --include="*.py" --include="*.ts"
```

Das Muster `\biss\b` trifft auch `issue`, `missing` nicht, aber `iss` als Teilwort in deutschen Bezeichnern schon (`Ergebnisse`). Fundstellen einzeln lesen; die Zahl allein ist kein Befund.

### Modus 2: code_review (Ort und Zeitpunkt)

Die Prüfung muss **vor** dem Token-Austausch stehen. Ein `iss`-Vergleich nach dem Einlösen ist wirkungslos: Der Code ist dann bereits beim falschen Server präsentiert.

**Pass-Pattern:**

```python
@app.get("/oauth/callback")
async def callback(request: Request, code: str, state: str, iss: str | None = None):
    flow = load_flow(state)                      # SEC-010: single-use, TTL
    expected = flow["issuer"]                    # beim Start aufgezeichnet
    supports_iss = AS_METADATA[expected].get(
        "authorization_response_iss_parameter_supported", False
    )
    if iss is None and supports_iss:
        raise HTTPException(400, "iss fehlt, obwohl der Issuer ihn ausstellt")
    if iss is not None and iss != expected:
        raise HTTPException(400, "iss stimmt nicht mit dem aufgezeichneten Issuer überein")
    return await exchange_code(code, flow)       # erst jetzt
```

### Modus 3: runtime_test

Drei Fälle, alle drei in die Evidenz: passender `iss` wird bedient; fremder `iss` wird abgewiesen; fehlender `iss` bei einem `iss`-fähigen Autorisierungsserver wird abgewiesen. Der erste Fall ist nicht optional — ohne ihn belegt eine Ablehnung nur, dass der Callback irgendetwas ablehnt.

## Pass Criteria

- [ ] Der erwartete Issuer wird **beim Start** des Flows aufgezeichnet, nicht aus der Rückkehr abgeleitet
- [ ] `iss` wird gegen diesen aufgezeichneten Wert geprüft, **bevor** der Code eingelöst wird
- [ ] Ein abweichender `iss` führt zum Abbruch, nicht zu einem Fallback auf den Default-Issuer
- [ ] Ein **fehlender** `iss` wird abgelehnt, wenn die Metadaten des Autorisierungsservers ihn ankündigen
- [ ] Der Vergleich ist exakt (String-Gleichheit auf dem Issuer-Identifier), nicht per Präfix oder Host-Vergleich
- [ ] **Evidence-Paar:** Tests belegen die Ablehnung bei fremdem `iss` **und** die Bedienung bei passendem
- [ ] Bei mehr als einem Autorisierungsserver: Die aufgezeichnete Zuordnung `state → issuer` ist serverseitig, nicht im Client-Parameter

## Common Failures

| Anti-Pattern | Konsequenz |
|---|---|
| `iss` nur geprüft, wenn vorhanden | Angreifer lässt ihn weg und umgeht die Prüfung vollständig |
| Prüfung nach dem Token-Austausch | Der Code ist bereits beim falschen Server präsentiert |
| Erwarteter Issuer aus der Rückkehr abgeleitet | Der Vergleich prüft einen Wert gegen sich selbst |
| Host-Vergleich statt Issuer-Identifier | Zwei Issuer auf einem Host sind ununterscheidbar |
| Zuordnung `state → issuer` clientseitig | Der Angreifer bestimmt, wogegen verglichen wird |
| Nur der Negativtest | Ein durchgehend kaputter Callback besteht |

## Remediation

Siehe Pass-Pattern oben. Zwei Punkte, die beim Nachrüsten regelmässig fehlen:

- **Den Issuer beim Flow-Start speichern.** In vielen Proxys existiert nur eine globale Konfiguration mit einem Issuer. Sobald ein zweiter dazukommt, ist der Vergleich gegen die Konfiguration falsch — er prüft gegen den Default, nicht gegen den, bei dem dieser Flow begann.
- **Die Metadaten des Autorisierungsservers einmal abrufen und zwischenspeichern**, sonst ist `authorization_response_iss_parameter_supported` bei jedem Callback ein Netzaufruf im kritischen Pfad.

## Effort

S — die Prüfung selbst sind wenige Zeilen. M, wenn die Zuordnung `state → issuer` erst eingeführt werden muss, weil der Proxy bisher nur einen Autorisierungsserver kannte.
