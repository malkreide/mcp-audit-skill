# SDK-006 — SDK-Major-Migration vollständig abgeschlossen

## Description

Ein Major-Sprung des Python-SDK (`mcp` 1.x → 2.x) wird selten in einem Zug fertig. Der mechanische Teil — Importe umbenennen — ist in einer Stunde erledigt und sieht danach vollständig aus. Was liegen bleibt, sind die Stellen, die **nicht** am Import hängen: ein Dependency-Bound, der noch das alte Ende festhält, ein schreibender Zugriff auf ein Objekt, das jetzt schreibgeschützt ist, ein Attributname, der still auf einen Alias fällt.

Diese Reste haben eine gemeinsame Eigenschaft: Sie brechen **nicht** dort, wo man testet. Ein Server mit halber Migration importiert sauber, startet auf stdio und besteht die Testsuite — und stirbt beim ersten HTTP-Deployment.

Der Check ist greppbar gehalten, weil er sonst nicht durchgeführt wird.

### Die fünf Kriterien

**1. Der Bound ist am neuen Major verankert, nicht als Deckel auf dem alten.**

`mcp>=1.0.0,<2` ist kein Zielzustand. Der Cap kauft Zeit — er hält das Projekt auf dem alten Major fest und verhindert, dass ein `pip install -U` es unbemerkt hinüberzieht. Als Dauerlösung sagt er: *wir sind nicht migriert, wir sind eingefroren.* Nach der Migration gehört der Bound ans andere Ende: `mcp>=2.0.0,<3`. Die obere Schranke bleibt, sie verankert nur nicht mehr die Vergangenheit.

**2. Keine Importe aus dem alten Modulpfad.** `mcp.server.fastmcp` existiert unter 2.x nicht mehr; der Pfad ist `mcp.server.mcpserver`, die Klasse `MCPServer` statt `FastMCP`.

**3. Keine Zuweisungen an `mcp.settings.<x>`.** Unter 2.x trägt `Settings` weder `host` noch `port`; die Zuweisung wirft `ValueError: "Settings" object has no field "host"`, ein lesender Zugriff `AttributeError`. Bind-Parameter gehen als Kwargs an `run()` bzw. an den App-Builder (siehe `SEC-016`).

**4. Tool-Annotations werden in snake_case gelesen.** `read_only_hint`, nicht `readOnlyHint`.

**5. Verschachtelte Manifeste sind erfasst.** Ein Repo mit einem zweiten Server unter `packages/`, `servers/` oder einem Unterverzeichnis hat eine zweite `pyproject.toml` mit eigenem Bound. Sie fällt durch jede Aufzählung, die Top-Level-Repos listet, und die Constraint des Elternprojekts erfasst sie nicht. Genau so ist ein Server im Portfolio als letzter auf 1.x liegen geblieben.

### Zu Kriterium 4: Was hier **nicht** gemeint ist

Das ist die Stelle, an der dieser Check leicht Schaden anrichtet, deshalb ausführlich:

**Das Drahtformat ist unverändert.** `readOnlyHint` überlebt unter 2.x als pydantic-**Alias**. Serialisiert wird in beiden Schreibweisen dasselbe JSON — nachprüfbar, indem man beide Formen serialisiert und vergleicht. Ein Client merkt von der Umstellung nichts, kein Wire-Traffic ändert sich, keine Kompatibilität bricht.

Was bricht, ist ausschliesslich der **lesende Zugriff im Python-Code**: `tool.annotations.readOnlyHint` findet das Attribut nicht mehr. Deshalb findet das ein Test und sonst niemand.

**Daraus folgt umgekehrt: In TypeScript-Servern ist camelCase korrekt und bleibt es.** Dort ist `readOnlyHint` der Feldname der Spec, nicht ein Alias. Dieser Check gilt für `sdk_language == "Python"` und sagt nichts über Node-Server aus. **Wer nach diesem Check einen TypeScript-Server auf snake_case „korrigiert", macht ihn kaputt.** Auch in Python-Servern ist camelCase beim *Schreiben* weiterhin gültig — nur der lesende Zugriff muss folgen.

### Abgrenzung zu `DEP-001` — dieselbe Zeile, zwei Fragen

Kriterium 1 sieht dieselbe Zeile an wie `DEP-001`, und die beiden Checks werden deshalb leicht verwechselt oder für redundant gehalten. Sie sind weder das eine noch das andere:

| | `SDK-006` (dieser Check) | `DEP-001` |
|---|---|---|
| **Frage** | Ist die Migration 1.x → 2.x **abgeschlossen**? | Ist der **Auflösungsraum** jeder Abhängigkeit begrenzt? |
| **Gegenstand** | ausschliesslich das Python-SDK `mcp` | jede Abhängigkeit der publizierten Distribution |
| **Was ein Cap bedeutet** | `<2` ist ein **Befund** — er verankert den alten Major, also ist nicht migriert worden | `<3` ist die **Erfüllung** — die Range hat beide Enden |
| **Wann erledigt** | einmalig, mit der Migration | dauerhaft, bei jeder Abhängigkeit und jedem Release |

In einem Satz: **Dieser Check prüft, an welchem Major der Bound verankert ist. `DEP-001` prüft, dass es überhaupt einen zweiten Bound gibt.**

Praktisch heisst das dreierlei. `mcp>=1.28.1` verletzt **beide** — hier den Major, dort die fehlende Obergrenze; das ist ein Befund je Check, nicht ein doppelter. `mcp>=2.0.0` ohne Cap verletzt ebenfalls beide, denn Kriterium 1 verlangt die obere Schranke mit. Und ein makelloses `mcp>=2.0.0,<3` erfüllt diesen Check vollständig, sagt aber **nichts** über `httpx`, `pydantic` oder `structlog` — die prüft `DEP-001`, und dieser Check sieht sie nie an.

Wer den einen Befund unter dem anderen abhakt, lässt eine der beiden Fragen unbeantwortet.

## Verification

### Modus 1: automated (die fünf Kriterien greppen)

```bash
# 1. Alle Manifeste finden — auch verschachtelte
find . -name pyproject.toml -not -path "*/.venv/*" -not -path "*/node_modules/*"

# Bound je Manifest prüfen
grep -rn --include=pyproject.toml -E '"mcp(\[[a-z]+\])?[><=]' .
#   ERWARTET:  mcp[cli]>=2.0.0,<3
#   BEFUND:    ...<2   oder   >=1.  — Deckel auf dem alten Major

# 2. Alter Modulpfad
grep -rn "mcp\.server\.fastmcp\|from fastmcp import\|FastMCP(" src/ tests/

# 3. Schreibende Settings-Zugriffe
grep -rnE "mcp\.settings\.[a-z_]+\s*=|\.settings\.(host|port)\s*=" src/ tests/

# 4. camelCase-LESEZUGRIFFE auf Annotations (nur Python!)
grep -rnE "\.(readOnlyHint|destructiveHint|idempotentHint|openWorldHint)\b" src/ tests/

# 5. Ist die Migration in der Testsuite überhaupt sichtbar?
grep -rn "mcpserver\|MCPServer" tests/ | head
```

**Pass:** Kriterien 2–4 liefern keine Treffer in `src/` und `tests/`; jedes gefundene Manifest trägt einen Bound am neuen Major.

Zu Kriterium 4 ein Hinweis zur Auswertung: Das Muster sucht **Attributzugriffe** (führender Punkt). Ein camelCase-Vorkommen in einem Dict-Literal oder einer JSON-Fixture ist beim Schreiben gültig und kein Befund. Und in `.ts`/`.js`-Dateien ist es ohnehin richtig — deshalb steht dort `src/ tests/` eines Python-Servers und kein repo-weites `grep -r`.

### Modus 2: runtime_test (der Pfad, der beim Import nicht bricht)

Die Migration ist genau dort unvollständig, wo `import` nichts merkt. Deshalb der Start auf **Netz-Transport**, nicht auf stdio:

```bash
MCP_TRANSPORT=streamable-http MCP_HOST=127.0.0.1 MCP_PORT=8000 \
  timeout 15 python -m my_mcp_server
# Pass: Server bindet und lauscht.
# Fail: ValueError: "Settings" object has no field "host"  → Kriterium 3 offen
```

Dazu die Annotations einmal wirklich lesen:

```python
tools = await session.list_tools()
for t in tools.tools:
    assert t.annotations is None or hasattr(t.annotations, "read_only_hint")
```

**Ein stdio-Start beweist hier nichts.** Er nimmt den Zweig, in dem weder Bind-Parameter noch App-Builder vorkommen — also genau die Stellen, an denen die Migration typischerweise hängengeblieben ist.

### Modus 3: config_check (CI hält den neuen Major fest)

```bash
grep -rn "mcp" .github/workflows/*.yml | grep -iE "install|pip|uv "
```

**Pass:** CI installiert aufgelöst gegen den neuen Bound, und mindestens ein Job führt die Suite gegen die tatsächlich installierte Version aus. Ein Lockfile, das noch 1.x festhält, während `pyproject.toml` 2.x sagt, ist derselbe halbe Zustand eine Ebene tiefer.

## Pass Criteria

- [ ] Jede `pyproject.toml` im Repo — auch verschachtelte — verankert den Bound am **neuen** Major (`>=2.0.0,<3`)
- [ ] Kein `<2`-Cap mehr, der den alten Major festhält
- [ ] Keine Importe aus `mcp.server.fastmcp` / `fastmcp` in `src/` oder `tests/`
- [ ] Keine schreibenden Zugriffe auf `mcp.settings.<x>`
- [ ] Bind-Parameter gehen als Kwargs an `run()` bzw. an den App-Builder
- [ ] Annotations werden in snake_case **gelesen** (`read_only_hint`)
- [ ] Der Server startet auf **Netz-Transport**, nicht nur auf stdio
- [ ] Lockfile und CI lösen gegen den neuen Major auf
- [ ] Kein TypeScript-Server wurde „mitkorrigiert" — dort ist camelCase richtig

## Common Failures

| Anti-Pattern | Konsequenz |
|---|---|
| `mcp>=1.0.0,<2` als Dauerzustand | Eingefroren statt migriert; der Cap sieht aus wie eine Entscheidung |
| Verschachtelte `pyproject.toml` übersehen | Ein Server im Repo bleibt auf dem alten Major und fällt durch jede Aufzählung |
| `mcp.settings.host = …` überlebt | `ValueError` beim Start auf HTTP-Transport — auf stdio unauffällig |
| Nur auf stdio getestet | Genau der Zweig, in dem die offenen Stellen nicht vorkommen |
| `.readOnlyHint` im Lesezugriff | `AttributeError` bzw. still `None`; kein Client merkt es |
| Lockfile hält 1.x, Manifest sagt 2.x | CI testet etwas anderes als das Manifest verspricht |
| **TypeScript-Server auf snake_case „korrigiert"** | Kaputt gemacht, was richtig war — dort ist camelCase der Spec-Feldname |
| Befund unter `DEP-001` abgehakt (oder umgekehrt) | Zwei Fragen an dieselbe Zeile: hier der verankerte Major, dort die Existenz der Obergrenze. Eine davon bleibt unbearbeitet |
| Aus grünem `DEP-001` auf grünes `SDK-006` geschlossen | Eine Obergrenze auf `mcp` sagt nichts darüber, an welchem Major sie hängt — `<2` ist gedeckelt und trotzdem unmigriert |

## Remediation

1. Alle Manifeste finden, bevor irgendetwas geändert wird — `find . -name pyproject.toml`. Ein Repo mit verschachteltem Server hat mehr als eines.
2. Bound umhängen: `>=2.0.0,<3`. Die obere Schranke bleibt; sie verankert nur nicht mehr die Vergangenheit.
3. Importe umstellen: `mcp.server.fastmcp` → `mcp.server.mcpserver`, `FastMCP` → `MCPServer`. Auch in Tests und Client-Hilfsmodulen.
4. Schreibende Settings-Zugriffe durch Kwargs an `run()` ersetzen.
5. Lesende Annotation-Zugriffe auf snake_case. **Nichts am Schreiben ändern und nichts an TypeScript-Servern.**
6. Einmal auf Netz-Transport starten. Das ist der einzige Schritt, der die Klasse Fehler findet, um die es hier geht.
7. Lockfile neu auflösen und CI gegen den neuen Bound laufen lassen.

```diff
- "mcp[cli]>=1.0.0,<2",
+ "mcp[cli]>=2.0.0,<3",
```

```diff
- from mcp.server.fastmcp import FastMCP
- mcp = FastMCP("my-server")
+ from mcp.server.mcpserver import MCPServer
+ mcp = MCPServer("my-server")

- mcp.settings.host = settings.host
- mcp.settings.port = settings.port
- mcp.run(transport=settings.transport)
+ mcp.run(transport=settings.transport, host=settings.host, port=settings.port)
```

## Effort

M — 1–3 Tage. Die Umbenennungen sind mechanisch; die Zeit geht in die verschachtelten Manifeste, den Start auf Netz-Transport und das Nachziehen der Tests.
